## 4. KEY ROTATION — `src/voice/keyring.ts`

### 4.1 The exact rotation predicate

`keyring.ts:89-94`:
```ts
release(key: AcquiredKey, ok: boolean, status?: number): void {
  key.material.fill(0);
  if (!ok && (status === 429 || status === 401 || status === 403)) {
    this.forceAdvance(key.pool, status === 429 ? 'rate-limited' : 'auth-failed');
  }
}
```

**Statuses that CAUSE rotation — exactly three, exhaustively:**

| HTTP status | Rollover reason recorded | Line |
|---|---|---|
| **429** | `'rate-limited'` | `keyring.ts:92` |
| **401** | `'auth-failed'` | `keyring.ts:92` |
| **403** | `'auth-failed'` | `keyring.ts:92` |

**Statuses that DO NOT cause rotation — exhaustively:**

| Case | Behaviour | Line |
|---|---|---|
| `ok === true` (any status) | No rotation. The `!ok` guard short-circuits. | `keyring.ts:91` |
| **400, 402, 404, 405, 409, 418, 422, 500, 502, 503, 504, and every other 4xx/5xx** | No rotation | `keyring.ts:91` |
| **`status === undefined`** | No rotation | `keyring.ts:91` |
| Any non-HTTP thrown value (TypeError, network blip, ZodError, JSON parse failure) | No rotation — `httpStatusOf` returns `undefined` | `errors.ts:69` |

### 4.2 What happens on an UNRECOGNISED status

`withKey` (`keyring.ts:138-166`) catches, then calls `ring.release(key, false, httpStatusOf(err))` (`keyring.ts:150`).

`httpStatusOf` (`src/common/errors.ts:51-70`) resolves the status from a thrown value, in this exact order:

| Input | Result | Line |
|---|---|---|
| `OrchestratorError` with `code === 'BRAIN_AUTH'` | **401** | `errors.ts:54` |
| `OrchestratorError` with `code === 'RATE_LIMITED'` | **429** | `errors.ts:55` |
| `OrchestratorError`, any other code | **`undefined`** | `errors.ts:57` |
| Any object with a numeric `.status` (groq-sdk `APIError`, or a bare fetch-shaped error) | that number verbatim | `errors.ts:61-62` |
| Any object with `error.status` numeric (openai/groq SDK wrapper) | that number verbatim | `errors.ts:64-67` |
| **Anything else — unrecognised status, non-object, string, `null`, `undefined`, network error, timeout, abort** | **`undefined`** | `errors.ts:69` |

`undefined` → `release(key, false, undefined)` → the `!== 429 && !== 401 && !== 403` test fails → **the pool is left alone and the key is still zeroed** (`keyring.ts:90` runs unconditionally). This is the documented fail-safe: `errors.ts:44-45` — *"an unrecognised failure must not advance the pool, or a transient 5xx would burn through a valid key pool."*

The rationale block at `errors.ts:47-49` and `keyring.ts:131-136` is explicit that 401 and 403 collapse to 401 "on purpose" — same user action, same rotation, and `release` only branches on 429-vs-auth.

**`KeyAdvanced` marker semantics** (`keyring.ts:160-163`): set only when the rollover log grew **and** `entry.from !== entry.to`. A single-key pool rotates K1→K1, which is a real event but not remediation, and is correctly not tagged. The marker is a non-enumerable `Symbol` (`keyring.ts:169`) so it can never reach `JSON.stringify` (telemetry) or a log line.

### 4.3 Slot arithmetic (verified against the code)

- `ROTATION_LIMIT = 10` (`keyring.ts:9`).
- `acquire` (`keyring.ts:75-87`): `slot = Atomics.add(view, 0, 1)`; `keyIndex = Math.floor(slot / 10) % list.length`. Request #0→#9 use K1; #10→#19 use K2. With a 1-key pool the index is always 0, so the key can never change — the pool is effectively pinned to a single credential until it is replaced.
- `forceAdvance` (`keyring.ts:97-108`): stores `ceil` to the next 10-slot boundary, then `nextKey = (currentKey + 1) % list.length`. With a 1-key pool this is `K1 → K1`: the rollover is logged but the same dead key is handed out on the next acquire. **A single-key pool cannot recover from a 401/403 by rotation** — it requires a new key in the vault. `key-store.ts:71` reports it as `1 key(s)`, so it is visible in `doctor`, but nothing warns at runtime.
- Callers: all production key uses go through `withKey` — `daemon.ts:157` (narrator), `daemon.ts:368` (coordinator chat), `daemon.ts:401` (STT), `daemon.ts:530` (prompt optimizer), `cli.ts:103` (live STT), `cli.ts:113` (live brain). Six sites, all `withKey`, all releasing with the real status.
